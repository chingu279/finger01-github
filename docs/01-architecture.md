# 01. 아키텍처 — 에이전트를 몇 개, 어떻게 나눌 것인가

## 왜 하나의 큰 에이전트로는 안 되는가

"건강 관리 에이전트" 하나에 모든 프롬프트를 넣으면 세 가지가 반드시 무너진다.

1. **안전이 희석된다.** 운동·식단·수면 지침 사이에 응급 판정 규칙이 섞이면
   대화가 길어질수록 안전 지침이 컨텍스트 뒤로 밀려 무시된다.
2. **책임 소재가 사라진다.** 잘못된 조언이 나왔을 때 어느 부분을 고쳐야 하는지 알 수 없다.
3. **개선이 불가능해진다.** 수면 조언을 손보면 운동 조언이 같이 변한다.

그래서 **역할별로 쪼개고, 안전은 에이전트가 아니라 코드로 내린다.**

## 전체 구조

```

   사용자 ─────────▶│   health-orchestrator    │  ← 단일 진입점
                    └────────────┬─────────────┘
                                 │ 항상 먼저: ./health brief
                    ┌────────────▼─────────────┐
                    │  결정적 코어 (LLM 아님)   │
                    │  triage · readiness ·    │  ← 여기서 나온 숫자와
                    │  baseline · report       │     안전 판정은 협상 불가
                    └────────────┬─────────────┘
        ┌────────────────────────┼────────────────────────┐
        │                        │                        │
  ┌─────▼──────┐          ┌──────▼──────┐          ┌──────▼──────┐
  │ L1 수집    │          │ L2 분석      │          │ L3 개입      │
  │ 3 agents   │─────────▶│ 3 agents     │─────────▶│ 4 agents     │
  └────────────┘          └─────────────┘          └──────┬──────┘
                                                          │
                                              ┌───────────▼──────────┐
                                              │ L4 순응 · 개선        │
                                              │ 3 agents             │
                                              └───────────┬──────────┘
                                                          │
                                       피드백 ────────────┘
                                       (다음 주 계획 + 시스템 자체 수정)
```

## 에이전트 카탈로그 — 총 14개

### L0. 오케스트레이션 (1)
| 에이전트 | 역할 | 왜 필요한가 |
|---|---|---|
| `health-orchestrator` | 단일 진입점. 팩트 확보 → 라우팅 → 답변 통합 | 사용자가 14개 에이전트를 외울 필요가 없어야 한다. 충돌하는 권고를 조정하는 심판도 필요하다 |

### L1. 수집 (3)
| 에이전트 | 역할 | 왜 필요한가 |
|---|---|---|
| `checkin-interviewer` | 대화형 주관 지표 수집 | 웨어러블은 기분·통증·스트레스를 모른다. 그런데 그게 가장 예측력이 높다 |
| `wearable-ingest` | 웨어러블/헬스앱 내보내기 파싱·정규화 | 단위 변환과 타임존 귀속에서 사고가 난다. 전담이 필요하다 |
| `clinical-record` | 검진·혈액검사·처방전 구조화 | 웨어러블이 절대 못 보는 층(지질, 간수치, 진단명)이 여기 있다 |

### L2. 분석 (3)
| 에이전트 | 역할 | 왜 필요한가 |
|---|---|---|
| `risk-triage` | 레드플래그 판정·에스컬레이션 | **가장 중요한 에이전트.** 다른 모든 것보다 우선한다 |
| `vitals-analyst` | 베이스라인 대비 이탈·추세 해석 | 숫자를 "무슨 일이 일어나는가"로 번역한다 |
| `insight-correlator` | 시차 상관에서 가설 도출 | "왜?"에 답하려면 여러 날에 걸친 관계를 봐야 한다 |

### L3. 개입 (4)
| 에이전트 | 역할 | 왜 필요한가 |
|---|---|---|
| `exercise-coach` | 준비도·부하 기반 운동 처방 | 도메인마다 근거·금기·실패 모드가 완전히 다르다. 한 프롬프트에 넣으면 전부 평범해진다 |
| `sleep-coach` | CBT-I 기반 수면 개선 | 〃 |
| `nutrition-coach` | 식단·수분·체중 | 〃 |
| `mind-coach` | 스트레스·명상·정서 | 〃 |

### L4. 순응 · 개선 (3)
| 에이전트 | 역할 | 왜 필요한가 |
|---|---|---|
| `adherence-agent` | 이행 추적, 미이행 원인 진단, 계획 수정 | **대부분의 건강 앱이 실패하는 지점.** 좋은 계획이 실행되지 않으면 나쁜 계획이다 |
| `experiment-designer` | N-of-1 실험 설계·판정 | 추측을 증거로 바꾸는 유일한 장치 |
| `reflection-agent` | 주간 회고 + **시스템 자체 개선** | 이게 없으면 시스템은 1주차 수준에 영원히 머문다 |

## 안전은 왜 에이전트가 아닌가

`safety-guard` 같은 15번째 에이전트를 만들고 싶어진다. **만들지 않는다.**

LLM은 프롬프트·맥락·대화 길이에 따라 출력이 흔들린다. "흉통 + 식은땀"을 놓치는 일이
100번 중 1번만 일어나도 이 시스템은 실패다. 그래서 안전은 `src/health/triage.py` 의
**결정적 규칙 엔진**이 판정하고, 에이전트는 그 결과를 **받아서 전달할 뿐 낮출 수 없다.**

| | 규칙 엔진 (코드) | 에이전트 (LLM) |
|---|---|---|
| 담당 | 레드플래그 판정, z-점수, 준비도, 부하 계산 | 해석, 코칭, 대화, 우선순위 |
| 특성 | 재현 가능, 테스트 가능, 감사 가능 | 유연, 맥락 반영, 비결정적 |
| 규칙 | 에이전트가 **완화 불가**, 상향만 가능 | 규칙 엔진 출력을 인용, 재계산 금지 |

이 경계가 이 아키텍처의 핵심이다.

## 데이터 흐름 (하루)

```
06:30  wearable-ingest    밤사이 수면·HRV·RHR 적재
07:00  checkin-interviewer 질문 3개 → data/daily/YYYY-MM-DD.json
07:01  [코어]             triage → readiness → brief   ※ LLM 개입 없음
07:02  risk-triage        레드플래그가 있으면 여기서 중단하고 에스컬레이션
07:03  orchestrator       vitals-analyst + 해당 코치들에게 병렬 위임
07:05  사용자             "오늘의 3가지"
22:00  adherence-agent    이행 여부 기록 → events.jsonl
일요일 reflection-agent   주간 회고 + 다음 주 실험 + 시스템 개선안
```

## 확장할 때의 원칙

새 에이전트를 추가하고 싶을 때 세 질문을 통과해야 한다.
1. 기존 에이전트의 프롬프트를 늘려서 해결되는가? → 그러면 추가하지 않는다.
2. 실패 모드가 기존 에이전트와 다른가? → 다르면 분리할 가치가 있다.
3. 결정적 코드로 만들 수 있는가? → 만들 수 있으면 **에이전트가 아니라 코드로 만든다.**
